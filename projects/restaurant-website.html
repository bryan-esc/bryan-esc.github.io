Building a Real Website for a Family Restaurant

A from-scratch, bilingual site for a real Austin restaurant, built mostly by hand, with a real serverless backend and a real deployment.

Live Site → Netlify Link → GitHub →

Background & Motivation

Angie's Mexican Restaurant is a real, family-run Tex-Mex spot in Austin, TX that's been open since 1993, and until this project it had no website of its own, just scattered listings on Yelp, Google, and Uber Eats. I'd worked there as a server, knew the menu and the regulars, and wanted to build the restaurant a real site.

Coming off a previous project that leaned heavily on machine learning, I deliberately wanted this one to be different: plain, understandable code I wrote mostly myself, with research built into the process instead of just shipping the first thing that worked.

The Constraints

  • No framework. Plain HTML, CSS, and JavaScript, on purpose. No React, no static site generator, no build step. I wanted to be able to read every line and know what it did.
  • Real customers. This wasn't a demo. The menu, hours, and prices all had to be accurate, and any real Google or Yelp reviews had to be reproduced faithfully rather than lightly rewritten, to stay on the right side of FTC guidance on testimonials.
  • A large menu. 18 categories and 104 items, several with size variants or à la carte add-ons, which made "just list everything" navigation a real usability problem.
  • Bilingual guests. Austin's East Side has a large Spanish-speaking customer base, so an English-only site wasn't good enough.
  • Budget. This is a small family business. The goal was to keep recurring costs at effectively $0, with the domain name as the only real expense.

Milestone 1

Organizing 104 Menu Items So People Can Actually Find Things

A flat list of 18 categories in a top nav is already a lot to scan, and I didn't want to just guess at ordering. I read into eye-tracking research on how people scan digital menus, the serial position effect (items at the start and end of a list get more attention than the middle), and the mere categorization effect (grouping items, even loosely, makes a large menu feel more navigable without removing anything).

18 → 7 Flat nav links consolidated into grouped dropdowns
1 Sticky sidebar that always shows where you are

That research drove two concrete decisions: a persistent sidebar built with position: sticky and the IntersectionObserver API, so it always highlights the category you're scrolled to, and later a restructure of the top navigation from 18 flat links into 7 grouped dropdown clusters (like "Tacos & Enchiladas" and "Soups & Salads"), so a first-time visitor isn't hit with 18 equally weighted choices at once.

It held up under real edge cases too. Reordering categories mid-project (moving Soups and Salads next to Entrees once I realized they work as full meals, not light starters) meant re-verifying the sidebar's highlighting logic, including the tricky case of the last category on the page, which can't always scroll to the same on-screen position as the others.

Milestone 2

A Real English/Spanish Toggle, Without Two Copies of the Site

Rather than maintain two separate sets of pages, every piece of text got a paired <span lang="en"> and <span lang="es" hidden>, with a single CSS rule and a small JavaScript toggle flipping which one shows. The choice is saved in localStorage, so it survives navigating between pages, and a small inline script runs before the page paints so there's no flash of the wrong language on load.

104 Menu items translated, plus nav, footer, and hours
1 Shared toggle across every page

The more interesting bug showed up after the feature already worked. Switching to Spanish, then accepting Chrome's built-in "translate this page" offer, then switching back to English inside the site could blank the entire page. Chrome's translator rewrites text nodes directly in the live DOM, and any of the site's own JavaScript that expects those nodes to be exactly as it left them (menus, carousels, the hours widget) can throw errors once they've been silently swapped out.

The fix wasn't patching around it. It was telling the browser not to offer its own translation on this site at all (<meta name="google" content="notranslate"> plus translate="no" on the <html> tag), since the site already ships a deliberate, human-reviewed translation of its own.

Milestone 3

A Real Backend, on a Static Site, for $0/Month

A fully static site has nowhere to send a contact form. Rather than bolt on a third-party form service, I built a small serverless function. It runs only when the form is submitted, checks a hidden honeypot field to silently reject spam bots, validates that the required fields are filled in, and then calls Resend's API to deliver the message as a real email.

$0 Per month, on free tiers
0 Secrets committed to the repo

The API key that authorizes those emails lives as an environment variable in Netlify's dashboard, never in a file in the repository. That distinction matters: a secret committed to git never fully disappears without rewriting history, even if a later commit deletes it, whereas an environment variable was never part of the code to begin with.

Getting real mail delivery working also meant verifying domain ownership with Resend through DNS records (standard email-authentication records, the same family as SPF and DKIM). Resend's free tier can't send to an arbitrary inbox until the sending domain is verified, which is what pushed the custom domain purchase earlier than originally planned.

Milestone 4

Going Live: Domain, DNS, and a Security Trade-off

Before buying a domain, I checked whether it was actually available, and found that angiesmexicanrestaurant.com already belonged to a completely unrelated "Angie's Mexican Restaurant" in Conroe, TX. Including the city (angiesmexicanaustin.com) turned out to be more than a workaround. It's also a small, free local-SEO signal for anyone searching "Mexican restaurant Austin."

1 Same-name restaurant already holding the obvious .com
On DNSSEC kept enabled instead of disabled for convenience

Connecting the domain to Netlify meant adding DNS records at the registrar, on top of the ones already added for Resend. Netlify's recommended record type (an ALIAS/ANAME record) was blocked because the domain has DNSSEC enabled, and the registrar doesn't allow ALIAS records on a DNSSEC-protected zone. Rather than turning off a real security feature to use the "nicer" option, I used Netlify's documented fallback, a plain A record pointing at their load balancer, which is the supported path for exactly this situation.

What I Learned

Two bug patterns kept recurring, and both taught me more than the features they were hiding inside. The first was simple but persistent: three HTML files that were supposed to match in structure (a stylesheet link, a script tag, a nav update) would quietly drift apart, because a change on one page didn't automatically reach the other two. The second was subtler: CSS specificity conflicts, where an older, more general rule kept silently overriding a newer, more specific one, so a fix would look correct in the code and still not show up on the page. Both taught me the same lesson: "the code looks right" and "the code is right" are different claims, and only one is worth trusting.

That pushed me toward verifying things concretely instead of eyeballing them: sampling rendered pixel colors to confirm real WCAG contrast ratios, writing small scripts to extract and diff translated content against a reference table instead of proofreading 104 items by eye, and stress-testing the homepage image carousel by clicking through it rapidly on purpose. That surfaced a real race condition where overlapping animations could leave two slides marked active at once. I fixed it with an explicit lock tied to the browser's actual transitionend event instead of a guessed timeout, then verified it with clicks landing a few milliseconds on either side of the transition's real boundary.

What Comes Next

A few menu items still need written descriptions, along with their Spanish translations once that text exists. After that, the natural next step is a dedicated proofreading pass on the Spanish content, mirroring the consistency pass already done on the English side.
